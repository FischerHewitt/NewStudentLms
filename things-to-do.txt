## SpeedGrader version mismatch warning
When the teacher grades a Submission, SpeedGrader should display the Assignment Version
that was live at the time of submission (the snapshot whose `published_at` is closest to
and before `submitted_at`). If this snapshot differs from the current published version,
show a banner in SpeedGrader: "This student submitted against an earlier version of the
instructions. You are grading based on what they were asked to do."

## Student notification: instructions updated after submission
When a student views an Assignment they have already submitted, and the current published
Assignment Version is newer than the one that was live at their `submitted_at`, show a
banner on their assignment view: "The instructions for this assignment have been updated
since you submitted. Your submission was recorded under the original instructions."
The banner should be informational only — it does not prompt re-submission (that is a
separate policy decision covered in "Resubmission policy" in ideas.txt).

## Assignment "published with pending edits" indicator
Currently the teacher Assignment view shows two states: Draft (no snapshot) and Published
(at least one snapshot exists). A useful third state would indicate when the teacher has
made edits to the live assignment row since the last published snapshot — i.e. students are
looking at an older version.

Implementing this requires diffing the live `assignments` row against the latest
`assignment_versions` snapshot (comparing instructions, due_date, points_possible, and
rubric criteria). If a diff is detected, show a badge like "Published · edits pending"
and a nudge to re-publish. Useful so teachers don't forget that students haven't seen
their revisions yet.

## Math text formatting (LaTeX / MathJax rendering)
Add support for rendering mathematical notation in assignment instructions, rubric
criteria, student submissions, and AI feedback. Teachers and students should be able
to write LaTeX syntax (e.g. \frac{d}{dx}, \sum_{n=1}^{\infty}) and have it render
as formatted math rather than raw text. Useful for MATH 143 and any STEM course.
Recommended approach: MathJax or KaTeX in the frontend, both work well with Next.js.
The submission text area would need a toggle between "plain text" and "math mode"
or a live preview panel so students can see their formatted output before submitting.


## Typed math input graded by AI (text input for math assignments)
Currently math quizzes and problem sets are submitted as file uploads (handwritten PDF/photo).
Add support for students to type math directly in the submission text area using LaTeX
or a structured input format. The AI can then grade typed math responses — checking
approach, intermediate steps, and final answer — without needing vision/OCR.
This is lower friction than uploading a photo and opens up AI grading for math
in the fast (non-snapshot) test suite since the input is plain text.
Useful beyond math: any course where students need to express formulas, chemical
equations, code snippets, or structured notation in their answers.

## Student coach question cap
The student chatbot (AI coach) currently has no usage limit. Add a per-assignment
question cap so students get a fixed budget of AI hints per assignment rather than
unlimited back-and-forth.

Design decisions to make:
  - Cap amount: suggest 5–10 questions per assignment as a starting point; make it
    configurable per assignment by the teacher (default 5).
  - What counts as a "question": each student message sent to the coach.
  - What happens at the cap: show a friendly message ("You've used all your AI hints for
    this assignment — try working through it on your own or ask your instructor."). Do NOT
    silently fail or give a generic error.
  - Persistence: track question count in a new coach_usage table (student_id,
    assignment_id, question_count) or add a column to submissions. Must survive page
    refresh — cannot be client-side only.
  - Teacher visibility: show the usage count per student in the SpeedGrader context so the
    teacher can see how much coaching a student needed.
  - Edge case: cap is per assignment, not per session. Refreshing the page or coming back
    the next day should not reset the counter.


## Accessibility tools and features
Add accessibility support so the LMS is usable by students and teachers with
disabilities. Target WCAG 2.1 AA compliance.

Key areas to address:

  Keyboard navigation:
  - All interactive elements (buttons, links, modals, tabs, course cards) must be
    reachable and operable via keyboard alone (Tab, Shift+Tab, Enter, Space, Escape).
  - Focus indicators must be visible — the current dark theme removes default outlines;
    add explicit focus-visible ring styles throughout.
  - Trap focus inside modals and drawers; return focus to the trigger on close.

  Screen reader support:
  - Add aria-label / aria-describedby to icon-only buttons (Grade, close, toggle).
  - Use aria-live regions for dynamic content: grading queue updates, coach responses,
    stat card refreshes, and loading states.
  - Ensure course cards convey health status and pending count semantically, not just
    visually (color alone is not sufficient).
  - Add role="status" or role="alert" for toast/notification messages.

  Color and contrast:
  - Audit all text/background combinations in the dark teacher dashboard for WCAG AA
    contrast ratios (minimum 4.5:1 for normal text, 3:1 for large text).
  - Muted text colors (rgba(238,240,255,0.35)) likely fail — increase opacity or darken
    background to meet threshold.
  - Never rely on color alone to convey meaning (health badges: Urgent/Watch/Steady
    use color + text label, which is good — keep this pattern everywhere).

  Motion and animation:
  - Wrap all CSS animations (alumos-fade-up, etc.) in a prefers-reduced-motion media
    query so users who have enabled reduced motion in their OS see no animation.
  - The Teacher Coach and other animated panels should also respect this preference.

  Forms and inputs:
  - All form fields (assignment submission textarea, coach input, generate-course form)
    must have explicit <label> elements or aria-label, not just placeholder text.
  - Error messages should be associated with their field via aria-describedby.
  - Required fields should be marked with aria-required="true".

  AI-generated content:
  - Coach responses and AI feedback should be announced to screen readers via an
    aria-live="polite" region so they don't interrupt ongoing reading.
  - Long AI responses should be structured with headings or lists, not a single
    paragraph blob, so screen reader users can navigate them efficiently.

  Testing approach:
  - Use axe-core or @axe-core/react in the test suite for automated a11y checks.
  - Manual audit with VoiceOver (macOS) and NVDA (Windows) for the two primary flows:
    student submission and teacher SpeedGrader review.
  - Add a Playwright a11y test that runs axe on every major page route.


## Business value analysis — cost savings vs. Canvas
Quantify and communicate the ROI of this LMS to make the case for adoption. Focus on
three angles: direct cost savings, time savings, and educational outcome improvements.

Brainstorm (to be refined into a formal doc):

  Direct cost savings vs. Canvas:
  - Canvas LMS licensing: ~$7–15 per student per year at the institutional tier, or
    ~$3,000–8,000/year for a small department. This LMS runs on Vercel + Supabase free/pro
    tiers — hosting cost for an MVP is effectively $0–50/month.
  - Third-party integrations (Turnitin, McGraw-Hill Connect, etc.): Canvas schools often
    pay $10–30/student/year per integration. Native AI grading eliminates Turnitin and
    reduces dependence on publisher homework platforms.
  - Estimate: a department of 500 students could save $5,000–15,000/year on licensing
    alone before factoring in time savings.

  Teacher time savings (the bigger number):
  - Grading time: a typical essay-based assignment takes 5–10 min per student to grade.
    At 30 students per class and 6 assignments per course, that's 9–18 hours of grading
    per course. AI SpeedGrader reduces this to ~30 sec per student (review + approve),
    saving ~80% of grading time. At $50/hr adjunct rate: $450–900 saved per course.
  - Feedback turnaround: AI grades within seconds vs. 3–14 days for human grading.
    Faster feedback is correlated with better learning outcomes (cite NWEA / Hattie).
  - Course creation: AI generates a complete course structure from a syllabus in ~30
    seconds vs. 2–4 hours of manual setup. For a new course: saves $100–200 of instructor
    prep time.

  Comparison surface vs. Canvas:
  - Canvas has no AI grading. Teachers still grade everything manually.
  - Canvas has no AI student coach. Students email the instructor or go to office hours.
  - Canvas course setup is fully manual — copy-paste syllabi into modules by hand.
  - This LMS's AI layer converts unstructured syllabi directly into graded course
    structures with rubrics, saving the manual translation step entirely.

  To build out:
  - Create a formal one-page cost comparison doc (docs/business/cost-comparison.md)
  - Add a pricing page or ROI calculator UI for the demo pitch
  - Gather real grading-time data from a pilot instructor to validate the 80% estimate
  - Quantify student outcome improvement if early data is available (grade distribution,
    resubmission rate, time-to-feedback correlation with scores)

## Define grading scale from the syllabus
When a teacher generates a course from a syllabus, the AI should extract the grading
scale (e.g. A = 90–100%, B = 80–89%, etc.) and store it on the Course. The gradebook
and student grade view should then display the letter grade alongside the numeric score.

Design decisions to make:
  - Where to store the grading scale: a JSONB column on the courses table
    (e.g. grading_scale: [{ letter: "A", min: 90 }, { letter: "B", min: 80 }, ...])
    is the simplest approach.
  - Generator behavior: if the syllabus contains an explicit grading scale, extract it.
    If not, default to a standard scale (A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, F < 60).
  - SpeedGrader: show the letter grade next to the numeric score when approving a grade.
  - Student grade view: show letter grade alongside final score on published grades.
  - Gradebook: add a letter grade column or show it in each cell tooltip.
  - Teacher editing: allow the teacher to edit the grading scale after course generation
    (e.g. if the syllabus used a non-standard scale or the AI extracted it incorrectly).
  - Edge case: plus/minus grades (A+, A-, B+, etc.) — decide whether to support them
    or flatten to whole letters for the MVP.
